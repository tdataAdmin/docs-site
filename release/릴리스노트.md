# 릴리스 노트

## 2026-09 월간 릴리스 — data-pipeline 설정 파일(`설정.json`) 필드 스키마

### 개요

`data-pipeline` 월간 릴리스 준비의 일환으로, 서비스 설정 파일 `설정.json`의 필드 타입과 필수 여부를 문서화합니다.
본 문서는 실제 설정 샘플(서비스명 `fixture-service`) 1건을 기반으로 JSON Schema(draft-07)를 추론한 결과를 정리한 것입니다.

- 대상 파일: `설정.json`
- 최상위 구조: `service`(object), `endpoints`(array) — 두 필드 모두 필수

### 필드 정의

#### 최상위

| 필드 | 타입 | 필수 | 설명 | 예시 값 |
| --- | --- | --- | --- | --- |
| `service` | object | 필수 | 서비스 식별 정보와 런타임 설정을 담는 블록 | — |
| `endpoints` | array&lt;object&gt; | 필수 | API 엔드포인트 목록 (primary / backup 등) | — |

#### `service` 객체

| 필드 | 타입 | 필수 | 설명 | 예시 값 |
| --- | --- | --- | --- | --- |
| `service.name` | string | 필수 | 서비스 이름 | `fixture-service` |
| `service.settings` | object | 필수 | 런타임 설정 블록 | — |

#### `service.settings` 객체

| 필드 | 타입 | 필수 | 설명 | 예시 값 |
| --- | --- | --- | --- | --- |
| `service.settings.timeout_sec` | integer | 필수 | 요청 타임아웃 (초 단위) | `30` |
| `service.settings.retry` | integer | 필수 | 요청 실패 시 재시도 횟수 | `3` |
| `service.settings.debug` | boolean | 필수 | 디버그 모드 활성화 여부 | `false` |

#### `endpoints[]` 배열 항목

| 필드 | 타입 | 필수 | 설명 | 예시 값 |
| --- | --- | --- | --- | --- |
| `endpoints[].name` | string | 필수 | 엔드포인트 식별자 | `primary`, `backup` |
| `endpoints[].url` | string | 필수 | 엔드포인트 URL (https) | `https://api.example.co.kr/v1`, `https://api-backup.example.co.kr/v1` |

### 참고 사항

1. **필수 여부 산정 방식**: 모든 필드가 샘플 1건에 포함되어 있어 전 필드가 `required`로 추론되었습니다. 기본값에 의존할 수 있는 필드(예: `debug`의 `false`)는 운영 정책상 선택(optional)으로 완화할지 검토가 필요합니다.
2. **숫자 범위 제약**: `timeout_sec`(30), `retry`(3)는 샘플에서 단일 값만 관측되어 min=max로 잡혔습니다. 릴리스 전 운영 허용 범위(예: `timeout_sec >= 1`, `retry >= 0`)로 재정의하는 것을 권장합니다.
3. **배열 구성 권장**: `endpoints`는 최소 1개(`primary`) 이상을 권장하며, `backup` 항목은 장애 대응용 이중화 구성입니다.

### 검증용 JSON Schema (draft-07)

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "service": {
      "type": "object",
      "properties": {
        "name": { "type": "string", "examples": ["fixture-service"] },
        "settings": {
          "type": "object",
          "properties": {
            "timeout_sec": { "type": "integer", "minimum": 30, "maximum": 30, "examples": [30] },
            "retry": { "type": "integer", "minimum": 3, "maximum": 3, "examples": [3] },
            "debug": { "type": "boolean", "examples": [false] }
          },
          "required": ["timeout_sec", "retry", "debug"]
        }
      },
      "required": ["name", "settings"]
    },
    "endpoints": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "name": { "type": "string", "examples": ["primary", "backup"] },
          "url": { "type": "string", "examples": ["https://api.example.co.kr/v1", "https://api-backup.example.co.kr/v1"] }
        },
        "required": ["name", "url"]
      }
    }
  },
  "required": ["service", "endpoints"]
}
```

## 2026-06-12 릴리스 — 멀티에이전트 파이프라인

> **섹션 생성 이력**: 본 섹션은 `main`에 없어 **신규 생성**되었습니다. 그간 2026-06-12 변경은 `release/주간배포노트.md`와 배포 관리자 공지 문구로만 언급되었고 릴리스노트에는 근거가 없었습니다.

### 개요

2026-06-12 배포로 `data-pipeline` 멀티에이전트 파이프라인에 도입한 **에이전트 메시지 전달**과 **도구 호출** 구조의 설계 근거를 arXiv **2308.08155** (*AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation*, v2 2023-10-03)에서 정리합니다. 논문의 두 축 — ① conversable agent + auto-reply, ② tool-backed agent — 을 고정 DAG 파이프라인에 어떻게 대응시켰는지가 범위이며, 논문 수치는 저자 통제 실험치로 우리 실측과 구분 표기했습니다.

### 근거 1 — 에이전트 메시지 전달 구조 (논문 §2.1–2.2)

| 논문 요소 | 논문 기술 | 2026-06-12 반영 |
| --- | --- | --- |
| conversable agent | 메시지를 전달(send)해 정보를 주고받고, 내부 컨텍스트는 주고받은 메시지 기반으로 유지된다. | 노드 간 전달 단위를 함수 인자 → **메시지 레코드**로 변경. 메시지 이력으로 상태를 복원하므로 재실행 시 컨텍스트 재구성 필요. |
| 통합 인터페이스 `send`/`receive`/`generate_reply` | 전 에이전트가 송수신 + 응답 생성이라는 단일 대화 인터페이스를 공유한다. | 태스크 인터페이스를 `execute`(계산) / `respond`(회신 메시지 생성)로 분리. 신규 에이전트는 인터페이스 구현만으로 접속. |
| auto-reply | 메시지 수신 시 **종료 조건 미충족이면** `generate_reply`를 자동 호출해 발신자에게 회신하며, 별도 control plane이 불필요하다. | DAG 정적 스케줄 대신 수신→자동 reply 트리거. 단 **`max_autoreplies`를 명시**해 무한 루프 차단, 종료는 설정값 + `TERMINATE` 문자열 2중 평가. |
| conversation programming | 계산은 대화 중심, 제어 흐름은 대화 주도. | 실패 조사를 "어떤 태스크가 죽었나" → **"어떤 메시지가 오가지 않았나"** 로그 조회로 전환. |
| 자연어+코드 제어 융합 | 시스템 메시지는 자연어로 재시도·출력 포맷·`TERMINATE`를 지시하고, 종료조건·인간입력·도구실행은 코드로 지정. | 프롬프트에 구조화 출력(`function_call` 형태) 강제, 재시도·타임아웃은 코드 설정으로만 통제(**프롬프트 단독 제어 금지**). |

### 근거 2 — 도구 호출 구조

| 논문 요소 | 논문 기술 | 2026-06-12 반영 |
| --- | --- | --- |
| tool-backed agent | 도구 에이전트는 코드 실행 또는 함수 실행으로 도구를 수행한다. | 도구 실행을 LLM 에이전트에서 분리해 **실행 전용 노드(executor)**. LLM은 제안만, 부작용은 executor만 발생. |
| AssistantAgent + UserProxyAgent 조합 | LLM 백엔드 assistant가 솔루션을 전달하면, 인간·도구 백엔드 user proxy가 실행 결과를 **피드백으로 회신**한다. | 우리 2-에이전트 기본형(생성 ↔ 실행)의 직접 대응. 실행 결과는 새 대화가 아니라 **발신자 회신 메시지**로 돌아가 재시도 판단에 사용. |
| 함수 호출 기반 동적 대화 | LLM이 대화 상태에 따라 함수 호출을 결정하고, 호출된 함수 안에서 추가 에이전트에 메시지를 전송해 동적 대화가 구동된다. | 매월 바뀌는 에이전트 범위를 정적 편성 대신 런타임 소환으로 허용. **등록부에 없는 이름이면 fail-fast.** |
| `GroupChatManager` | 화자 동적 선택 → 응답 수집 → 브로드캐스트 반복. | **본 릴리스 미사용.** 도입 시 화자 선택 근거를 로그에 남겨야 한다. |
| 부작용 안전 경계 | 코드·함수 호출로 외부 환경(패키지 설치 등)을 바꾸는 것은 위험할 수 있다고 명시. | executor는 allow-list 밖 명령·설치 차단, **쓰기를 동반하는 도구**는 검증 통과 후 실행. (관련 #5 `database is locked`, #9·#10) |

### 후속 실험

`data-pipeline` **#13**에서 선별한 순위와 동일하며, 본 릴리스 근거인 AutoGen을 기준선으로 둡니다.

| 순위 | arXiv | 반영할 구조 | 검증 지표 |
| --- | --- | --- | --- |
| 기준선 | 2308.08155 | 위 §근거 1·2 (메시지 전달 + auto-reply + 도구 백엔드 분리) | reply 왕복 수 / 종료 조건 미충족 세션 / 제안-실행 정합률 |
| 1 | 2602.16873 AdaptOrch | 태스크 DAG에서 4개 토폴로지 런타임 라우팅 — 월간 범위 변동의 직접 대응 | 편성 소요, 라우팅별 비용·지연 |
| 2 | 2608.02645 Verified Tool Calls | 비원자적 실패에 postcondition 검증·verify-before-retry·멱등성 키 | 현행 `retry=3` 정책 재검토, 중복 실행 건수 |
| 3 | 2606.13707 Orchestra-o1 | 온라인 서브에이전트 전문화 | 신규 에이전트 접속 후 회귀 |

### 유의사항

1. **논문 수치는 저자 실험치이며 우리 실측이 아닙니다.** AutoGen의 OptiGuide 코드 430줄→100줄, unsafe 식별 F-1 +8%/+35%, ALFWorld +15%는 모두 원 저자 결과입니다. 우리 실측은 #5(SUCCESS 18 / FAILED 8)·#7·#9·#10 참조 — 두 수치를 한 표에 섞지 마십시오.
2. 본 섹션은 문서화이며 배포 검증을 대체하지 않습니다. `data-pipeline` `main`의 2026-06-12 전후 커밋에는 구조 변경을 직접 나타내는 커밋이 관측되지 않아(확인된 2건은 `Initial commit`, `docs: 프로브 검증용 고정 파일 추가`), 구현 PR 커밋 해시를 본 섹션에 연계해 확정합니다.
3. `설정.json`에 에이전트 대화 키(`max_autoreplies`, 도구 allow-list, 등록부)가 아직 없습니다. `retry`와 auto-reply 상한은 **서로 다른 정책**으로 분리해야 합니다.
4. `GroupChatManager` 대응 기능은 미구현이므로 릴리스 기능 범위로 공지하지 마십시오.
