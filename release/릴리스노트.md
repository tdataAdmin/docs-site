# 릴리스 노트

## 2026-09 월간 릴리스 — data-pipeline 설정 파일(`설정.json`) 필드 스키마

### 개요

`data-pipeline` 월간 릴리스 준비의 일환으로, 서비스 설정 파일 `설정.json`의 필드 타입과 필수 여부를 문서화합니다.
본 문서는 실제 설정 샘플(서비스명 `fixture-service`) 1건을 기반으로 JSON Schema(draft-07)를 추론한 결과를 정리한 것입니다.

- 대상 파일: `설정.json`
- 최상위 구조: `service`(object), `endpoints`(array) — 두 필드 모두 필수

### 필드 정의

#### 최상위

| 필드 | 타입 | 필수 | 설명 | 예시 값 |
| --- | --- | --- | --- | --- |
| `service` | object | 필수 | 서비스 식별 정보와 런타임 설정을 담는 블록 | — |
| `endpoints` | array&lt;object&gt; | 필수 | API 엔드포인트 목록 (primary / backup 등) | — |

#### `service` 객체

| 필드 | 타입 | 필수 | 설명 | 예시 값 |
| --- | --- | --- | --- | --- |
| `service.name` | string | 필수 | 서비스 이름 | `fixture-service` |
| `service.settings` | object | 필수 | 런타임 설정 블록 | — |

#### `service.settings` 객체

| 필드 | 타입 | 필수 | 설명 | 예시 값 |
| --- | --- | --- | --- | --- |
| `service.settings.timeout_sec` | integer | 필수 | 요청 타임아웃 (초 단위) | `30` |
| `service.settings.retry` | integer | 필수 | 요청 실패 시 재시도 횟수 | `3` |
| `service.settings.debug` | boolean | 필수 | 디버그 모드 활성화 여부 | `false` |

#### `endpoints[]` 배열 항목

| 필드 | 타입 | 필수 | 설명 | 예시 값 |
| --- | --- | --- | --- | --- |
| `endpoints[].name` | string | 필수 | 엔드포인트 식별자 | `primary`, `backup` |
| `endpoints[].url` | string | 필수 | 엔드포인트 URL (https) | `https://api.example.co.kr/v1`, `https://api-backup.example.co.kr/v1` |

### 참고 사항

1. **필수 여부 산정 방식**: 모든 필드가 샘플 1건에 포함되어 있어 전 필드가 `required`로 추론되었습니다. 기본값에 의존할 수 있는 필드(예: `debug`의 `false`)는 운영 정책상 선택(optional)으로 완화할지 검토가 필요합니다.
2. **숫자 범위 제약**: `timeout_sec`(30), `retry`(3)는 샘플에서 단일 값만 관측되어 min=max로 잡혔습니다. 릴리스 전 운영 허용 범위(예: `timeout_sec >= 1`, `retry >= 0`)로 재정의하는 것을 권장합니다.
3. **배열 구성 권장**: `endpoints`는 최소 1개(`primary`) 이상을 권장하며, `backup` 항목은 장애 대응용 이중화 구성입니다.

### 검증용 JSON Schema (draft-07)

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "service": {
      "type": "object",
      "properties": {
        "name": { "type": "string", "examples": ["fixture-service"] },
        "settings": {
          "type": "object",
          "properties": {
            "timeout_sec": { "type": "integer", "minimum": 30, "maximum": 30, "examples": [30] },
            "retry": { "type": "integer", "minimum": 3, "maximum": 3, "examples": [3] },
            "debug": { "type": "boolean", "examples": [false] }
          },
          "required": ["timeout_sec", "retry", "debug"]
        }
      },
      "required": ["name", "settings"]
    },
    "endpoints": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "name": { "type": "string", "examples": ["primary", "backup"] },
          "url": { "type": "string", "examples": ["https://api.example.co.kr/v1", "https://api-backup.example.co.kr/v1"] }
        },
        "required": ["name", "url"]
      }
    }
  },
  "required": ["service", "endpoints"]
}
```

## 2026-06-12 릴리스 — 멀티에이전트 파이프라인

> **섹션 생성 이력**: 본 섹션은 `main`에 존재하지 않아 **신규 생성**되었습니다. 그간 2026-06-12 멀티에이전트 파이프라인 변경은 `release/주간배포노트.md`와 배포 관리자의 공지 문구로만 언급되었고, 릴리스노트에는 근거가 남아 있지 않았습니다 (`주간배포노트.md` 하단 "확인 결과 — 매출 CSV 스키마 변경 안내 누락"에서 동일 문제 지적).

### 개요

2026-06-12 배포로 `data-pipeline` 멀티에이전트 파이프라인에 도입한 **에이전트 간 메시지 전달 구조**와 **도구(tool) 호출 구조**의 설계 근거를 arXiv **2308.08155** (*AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation*, v2, 2023-10-03)에서 정리합니다.

논문이 제시한 두 축 — ① **conversable agent + auto-reply**(대화로 제어 흐름을 표현) ② **tool-backed agent**(코드/함수 실행을 별도 에이전트 역으로 분리) — 을 고정 DAG 파이프라인에 어떻게 대응시켰는지가 본 섹션의 범위입니다. 논문의 추상 개념과 우리 구현은 아래 표에서 "반영" 열로만 연결했으며, **논문의 성능 수치는 저자 통제 실험치**로 우리 실측과 구분해 표기했습니다.

### 근거 1 — 에이전트 메시지 전달 구조

| 논문 요소 (2308.08155 §2.1–2.2) | 논문 기술 내용 | 2026-06-12 파이프라인 반영 |
| --- | --- | --- |
| conversable agent | 에이전트는 다른 에이전트에게 메시지를 **전달(send)** 해 정보를 주고받으며, 메시지 수신·반응·응답이 가능한 상태로 설계된다. 내부 컨텍스트는 **주고받은 메시지 기반으로** 유지된다. | 노드(state) 간 전달 단위를 "함수 인자"에서 "메시지 레코드"로 변경. 노드는 입력 메시지와 자신이 쓴 메시지만으로 상태를 복원하므로, 재실행 시 컨텍스트 재구성이 필요하다. |
| unified interface (`send` / `receive` / `generate_reply`) | 모든 에이전트가 메시지 송수신 함수와 "행동 수행 + 응답 생성" 함수라는 **단일 대화 인터페이스**를 공유한다. | `execute`(계산)와 `respond`(다음 노드로 넘길 메시지 생성)로 태스크 인터페이스를 분리. 새 에이전트 추가 시 오케스트레이터 수정이 아니라 인터페이스 구현만으로 접속된다. |
| auto-reply 메커니즘 | 메시지를 받으면 **종료 조건이 충족되지 않는 한** `generate_reply`를 자동 호출해 **발신자에게 회신**한다. reply 함수 등록 + 대화 초기화만으로 흐름이 유도되어 **별도의 제어 평면(control plane)이 필요 없다.** | DAG 정적 스케줄 대신 "수신 → 자동 reply" 트리거를 도입, 단 **`max_autoreplies`(종료 조건)를 반드시 명시**해 무한 대화 루프를 차단. 종료 조건은 Python 설정(`max_autoreplies`)과 메시지 내 `TERMINATE` 문자열 2중으로 평가. |
| conversation programming (computation / control flow) | 계산은 대화 중심적(행동은 후속 대화를 위한 메시지 전달로 귀결)이고, 제어 흐름은 대화 주도적이다. | 파이프라인 실패 조사를 "어떤 태스크가 죽었나"가 아니라 **"어떤 메시지가 오가지 않았나"** 로그 조회로 전환. 메시지 이력이 곧 실행 기록이 된다. |
| 자연어 + 프로그래밍 언어 제어 융합 | 기본 시스템 메시지가 자연어로 재시도·출력 포맷·종료(`TERMINATE`)를 지시하고, 종료 조건·인간 입력 모드·도구 실행 로직은 코드로 지정한다. | 에이전트 프롬프트에 출력 스키마(`function_call` 형태의 구조화된 응답)를 강제하고, 재시도·타임아웃은 코드 설정으로만 통제 — **프롬프트에만 의존하는 제어 금지**. GPT-3.5 계열은 지시 이행률이 낮아 프롬프트 단독 제어를 허용하지 않음. |

### 근거 2 — 도구 호출 구조

| 논문 요소 | 논문 기술 내용 | 2026-06-12 파이프라인 반영 |
| --- | --- | --- |
| tool-backed agent | 도구 기반 에이전트는 **코드 실행 또는 함수 실행**으로 도구를 수행한다. 기본 user proxy agent는 LLM이 제안한 코드를 실행하거나 LLM이 제안한 함수 호출을 수행할 수 있다. | 도구 실행을 LLM 에이전트 내부에서 떼어내 **실행 전용 노드(executor)** 로 분리. LLM은 "실행 제안"만 하고 실제 부작용은 executor만 발생시킨다. |
| LLM + 인간/도구 하이브리드 조합 | `AssistantAgent`(LLM 백엔드)와 `UserProxyAgent`(인간·도구 백엔드)라는 사전 구성 서브클래스를 조합해 시스템을 구성한다. assistant가 솔루션을 전달하면 user proxy가 인간 입력을 받거나 **코드를 실행해 결과를 피드백으로 회신**한다. | 우리 2-에이전트 기본형(`생성 에이전트 ↔ 실행 에이전트`)은 이 조합의 직접 대응이다. 실행 결과는 새 대화가 아니라 **이전 발신자에 대한 회신 메시지**로 되돌아가 재시도 판단에 사용된다. |
| 도구 호출 기반 동적 대화 | LLM이 대화 상태에 따라 특정 함수 호출 여부를 결정하고, **호출된 함수 안에서 추가 에이전트에 메시징**함으로써 동적 멀티에이전트 대화가驱动力된다. (customized `generate_reply`도 동일 목적의 두 번째 경로) | 월 단위로 바뀌는 멀티에이전트 범위를 정적 편성이 아니라 "실행 중 함수 호출로 추가 에이전트 소환" 형태로 허용. 단 호출 대상은 등록부(registry)에 없는 이름이면 즉시 실패(fail-fast). |
| `GroupChatManager` | 화자를 **동적 선택 → 응답 수집 → 전체 브로드캐스트** 3단계로 반복한다. 역할 기반(role-play) 프롬프트가 작업 기반 프롬프트보다 화자 선택에서 더 효과적이었다고 보고한다. | 다중 참조(dashboard/report 등) 구간에만 도입을 검토 중. **본 릴리스에서는 미사용**이며, 도입 시 화자 선택 근거를 로그에 남겨야 한다. |
| 부작용에 대한 안전 경계 | LLM 에이전트가 코드 실행·함수 호출로 외부 환경(예: 패키지 설치)을 변경하는 것은 **위험할 수 있다**고 명시하고, safeguards 요구를 ethical consideration으로 기재한다. | executor 노드는 allow-list 밖 명령·패키지 설치를 차단하고, 쓰기을 동반하는 도구는 검증 단계 통과 후 실행. (동일 계열 이슈: #5 `database is locked`·`deadlock detected`, #9·#10 재시도 계열) |

### 유의사항 (수치 혼용 금지)

1. **논문 수치는 저자 통제 실험치이며 우리 파이프라인 실측치가 아닙니다.** 예로 AutoGen이 보고한 OptiGuide 재구현의 코드량 감소(430줄 → 100줄), unsafe 코드 식별 F-1 개선(+8% GPT-4 / +35% GPT-3.5-turbo) 및 ALFWorld grounding agent +15%는 **모두 원 저자 실험 결과**입니다. 우리 파이프라인의 실패·편차 실측치는 #5(SUCCESS 18 / FAILED 8), #7, #9, #10에 별도로 정리되어 있으며 두 수치를 한 표에 섞지 마십시오.
2. 본 섹션은 **문서화이며 배포 검증을 대체하지 않습니다.** `data-pipeline` `main`의 2026-06-12 전후 커밋에는 멀티에이전트 구조 변경을 직접 나타내는 커밋이 관측되지 않습니다(`주간배포노트.md` §"2026-10-03 주차 — data-pipeline 커밋 내역"에서 확인된 커밋 2건은 `Initial commit`, `docs: 프로브 검증용 고정 파일 추가`). 구조 반영 여부는 구현 PR 병합 후 커밋 해시를 본 섹션에 연계해 확정합니다.
3. `설정.json`에는 아직 에이전트 대화 관련 키(`max_autoreplies`, 도구 allow-list, 에이전트 등록부)가 정의되어 있지 않습니다. 후속 실험 진입 전 `설정.json` 필드 스키마(위 2026-09 섹션)에 해당 키를 추가하고, `retry` 값과 auto-reply 상한을 **서로 다른 정책**으로 분리해야 합니다.
4. `GroupChatManager` 대응 기능은 미구현 상태이므로 릴리스 기능 범위로 공지하지 마십시오.
